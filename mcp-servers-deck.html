01 · The case

Integration stops being a project and becomes a property

Every AI initiative we've funded so far has paid for its own plumbing, and thrown it away when the project ended. MCP inverts that: the plumbing is built once per system and consumed by everything that comes after — including the surfaces we haven't bought yet.

01 Cost grows with parts, not pairs

One server per system, one client per surface — each priced once, however many things end up consuming it. The dials on the previous slide are the whole finance case.

02 Capability compounds

The first server serves one surface. The seventh serves every surface built so far and every one built later. Value accrues multiplicatively while cost accrues linearly — that is the entire strategic argument.

03 Time-to-value collapses

A new use case stops being a build and becomes a wiring exercise. "Can the agent see contract history?" goes from a quarter of engineering to an afternoon, once crm-mcp exists.

04 No bottleneck team

The team that owns the system owns its server, its auth, and its release cadence. There is no central integrations group for twelve roadmaps to queue behind.

05 Vendor optionality is real

MCP is a Linux Foundation project with a published twelve-month deprecation policy, and it is model-agnostic. Swap the model, swap the host, keep the integrations. That is a procurement argument, not an engineering one.

06 Governance gets one surface

Forty bespoke integrations means forty auth stories and no audit trail. One protocol means one place to enforce OAuth, rate limits, approval gates and logging — for every agent, retroactively.

02 · Why it matters

Connect each system once, not once per tool

Today every AI tool needs its own connection to every system it touches. Each one is built separately, by whoever needed it, and none of them can be reused. A shared standard replaces all of that with one connection per system and one per tool — built once, used by everything that comes after.

Build it once, use it everywhere

The first connection helps one team. The fifth helps every AI tool we already run, and every one we adopt later, at no additional integration cost. Spend rises in a straight line; what the organisation can actually do rises much faster.

Whoever owns the system owns its server

No central integration team for a dozen roadmaps to queue behind. Whoever runs the system publishes the connection, sets its access rules, and owns it on their own schedule.

An open standard, not a vendor API

MCP is a Linux Foundation project and works with any model. Change the model or the vendor later and the integrations stay where they are — and because every system ends up described the same way, the portfolio gets more legible as a side effect.

This already works at scale

Uber runs 1,500+ active agents across 10,000+ internal services this way — roughly 60,000 agent runs a week, all of it through MCP servers fronting systems they already had.

07 · Why not just call the API?

Why not just let it call the API?

This is the question that decides everything, and the answer is one idea. Intent is what someone wants, in their own words. Mapping it is turning that into concrete calls — which operations, in what order, with which arguments. With an API a developer does that mapping while building, and freezes it into code. With MCP the model does it while running.

And this is what moving it buys

The combinatorial argument

A team ships the workflows it anticipated — a dozen screens, a dozen endpoints. A dozen well-described tools compose into far more useful sequences than anyone will ever enumerate, including the ones your users invent three months after launch.

Composition is only as good as the descriptions

The model picks a route by reading prose. Two tools whose descriptions do not say when to prefer one over the other will be chosen between at random — which looks like a model problem and is actually a writing problem.

And it will sometimes compose wrongly

A non-deterministic chooser will occasionally pick a bad path. That is precisely why the approval gate, the per-tool rate limit and the audit log are load-bearing rather than ceremonial.

08 · One question, four tools

You stop shipping features. You start shipping capabilities.

This is what run-time mapping buys, and it is easiest to see with a real example. Four tools, described once, ordered by nobody — answering two questions that no one wrote code for.

What it retires

The backlog item that reads “can it also show me…”. That used to be a new endpoint, a new screen and a release. Once the underlying capability is exposed and described, it is frequently nothing at all.

09 · A layer above, not a better API

Not a better API — a layer above one

MCP does not compete with REST or GraphQL, and it is not faster, leaner or more elegant than either. It sits on top of them, and an MCP server is usually a thin façade over endpoints you already run.

“But we already have GraphQL”

The fairest challenge on this slide, because GraphQL genuinely shares three of MCP's properties: one endpoint, a typed schema, and run-time introspection. Three things still separate them.

Introspection is not description

A schema says Customer.orders: [Order!]!. It cannot say “don't span more than 90 days or this times out”, or “use lifetimeValue, not the sum of orders, because of refunds.” That knowledge currently lives in the heads of four people. A tool description is where it goes.

The schema doesn't fit in the prompt

You cannot hand a real federated graph to a model — introspection alone runs to tens of thousands of tokens. Curation isn't a limitation of MCP, it's the requirement. Eight tools fit; your whole graph never will.

Arbitrary query power is a liability here

A model that can write any query can write a catastrophically expensive one. search_incidents(query, limit≤50) cannot become a full scan. Narrowing what's expressible is the feature, not the compromise.

If you have a good graph, wrap it

Our data-domain server should call the federated graph, not the databases behind it. GraphQL already solved federation; MCP adds description, bounding and approval on top. They compose — this is not an either/or.

Where MCP is the wrong tool

It is an agent access path, not a data plane. Bulk ETL, high-throughput streaming and low-latency service-to-service calls stay exactly where they are. If no model is in the loop, MCP is pure overhead.

The migration is additive

Nothing gets ripped out. A server is a new, thin consumer of endpoints that already exist — which is why the first one is a two-week job and not a re-platforming.

04 · MCP and A2A

Two protocols, two axes — we will run both

MCP connects an agent down to tools and data. A2A connects an agent across to another agent. They are complementary by design, and production stacks already combine them.

The combined pattern, in one sentence

18 · What it could become

What becomes possible once the mesh exists

Now that the mechanism is clear, here is the destination. The transformation isn't "we get a chatbot" — it's that every system worth querying becomes reachable by any agent, under one auth and audit story, and the marginal cost of the next use case falls to roughly zero.

How organisations actually get there

STAGE 01
One server, one team

A single domain team exposes three tools. Value is local; the point is to learn the shape and set the pattern. ~2 weeks.

STAGE 02
Gateway and guardrails

OAuth, per-tool rate limits, audit logging and an approval policy land once, centrally. Every later server inherits them. ~1 quarter.

STAGE 03
Domain teams self-serve

A template repo and a review checklist mean teams ship servers without asking permission. Server count starts compounding.

STAGE 04
Capability mesh

New agents are assembled from existing servers in days rather than built over quarters, because the underlying capabilities already exist and are described.

What it looks like in four functions — pick the two in the room

Engineering & SRE

Triage that spans observability, deploy history and the codebase in one turn: "what changed before this Sev2, and who owns it?"

Servers: incidents · deploys · repo · metrics

Revenue & sales

Account history, current pricing, contract terms and open support tickets assembled before a call — without a rep opening five tabs.

Servers: crm · pricing · contracts · support

Finance

Close-process reconciliation across the ERP, the warehouse and the policy handbook — with the policy shipped as a prompt, so the method is the same every month.

Servers: erp · warehouse · policy

Data & analytics

Governed natural-language access: the catalogue server decides what's queryable, so access control lives in one place instead of in every prompt.

Servers: catalog · warehouse · lineage

What it quietly retires

The one-off iPaaS flows, the RPA scripts that break on a UI change, and the four internal chatbots that each built their own Jira integration. Those become one server with an owner.

The second-order effect

Once capabilities are described well enough for a model to choose between them, they're described well enough for a person to find. Teams start discovering systems they didn't know they were allowed to query.

The honest constraint

This is the same mechanism as a data-exfiltration surface, built quickly and with enthusiasm. An agent with our CRM, our warehouse and our email server is exactly as useful and exactly as dangerous as it sounds.

So: gateway before proliferation. Stage 02 is not optional overhead — it is the thing that lets Stage 03 happen without a security review blocking every team. Slide 15 is the checklist.

06 · The three roles

Host, client, server

People say “MCP server” loosely. The spec is precise, and the precision matters the moment you draw a trust boundary. Four parts, three relationships — the order they fire in is the next slide.

01 Host

The application the human is using — Claude Desktop, an IDE, our own agent runtime. It holds the model, the conversation, and the permission prompts. It decides what the model is even allowed to see.

02 Client

A connector inside the host, one per server. It speaks MCP, keeps no session (as of this revision), and translates between protocol messages and whatever the host's model loop needs.

03 Server

What you build. A process or an HTTP endpoint that exposes tools, resources, and prompts. It never talks to the model directly — it answers requests and returns content.

The server never sees the model

It cannot prompt it, cannot read the conversation, and gets only the arguments the host chose to send. That boundary is the security story — and it is why step 06 of the next slide is the only place your systems are exposed.

So which model is it? Whichever the host uses

The protocol never names one. Nothing in tools/list or tools/call refers to a model, and the server never learns which one is on the other side — Claude, Gemini, GPT, an open-weight model you host yourself. The only hard requirement is reliable tool calling.

Choosing well from forty tools is a real capability difference between models, but that is a host-side decision we can revisit later without touching a single server.

Human in the loop is a MUST-adjacent SHOULD

The spec says clients SHOULD show tool inputs to the user before calling, and provide UI to deny invocations. Step 04 on the next slide is where that lives. Our host implementations need to honour it, not stub it.

Presenter note

The point: three roles. We build the server, and it is the most constrained of the three.

Say: “The server never sees the model. It cannot prompt it, cannot read the conversation, and gets only the arguments the host chose to send.”

If asked: which model? — any model that can do tool calling; the server never learns which one. Swapping it changes nothing below the host.

MCP-Protocol-Version

Required on every POST. Must match _meta in the body, or the server returns -32020 HeaderMismatch.

Mcp-Method / Mcp-Name

Required. Mirrors method and params.name so gateways can route, meter, and rate-limit per tool.

_meta carries the state

Protocol version and client capabilities on every single request. That is what makes the server stateless.

Where the tool list came from

Not from this request. At startup — or when a cached list expires — the client sends tools/list to each configured server and gets back every tool's name, description and inputSchema. The host merges the lists from all its servers, translates them into its provider's format, and pastes the result into step 02's prompt.

And it stays fresh without polling

tools/list results carry required ttlMs and cacheScope fields, and servers SHOULD return tools in a deterministic order — so the client cache and the model's own prompt cache both keep hitting. When the set changes, the server pushes notifications/tools/list_changed to clients that opted in, and they re-fetch.

Two protocols, not one

Steps 1–3 are the model provider’s API and our own approval UI — different formats, different vendors, nothing standardised by MCP. Steps 4–7 are MCP. The server only ever sees the second half.

07 · Reference architecture

What a typical enterprise setup looks like

Five layers. The only new infrastructure is the middle one — and it is where every control you care about lives.

Put these five things in the gateway, once

OAuth 2.1 token validation mapped to tool scopes · rate limits keyed on Mcp-Name, so one runaway agent cannot exhaust a downstream system · an audit record per call including the arguments · Origin validation · header/body agreement checks.

Five things, built once, inherited by every server that follows.

Who owns what

Platform owns the gateway, the server template and the review checklist. Domain teams own their server, its tool descriptions, and its downstream credentials. Nobody owns "integrations" as a function — that's the point.

Scope tools to the token, not the connection

The tool list MUST NOT vary per connection — but it MAY vary by the authorisation presented on the request. That is the supported way to show a support engineer fewer tools than an SRE, and it's exactly where the gateway earns its place.

Trace it end to end

traceparent in _meta is reserved for W3C Trace Context, matching the OpenTelemetry conventions for MCP. One agent turn spanning six tool calls across four servers is a single trace, not a mystery.

And a curated registry beside it

The gateway enforces policy at call time; a private registry decides what is allowed to exist at all. Public registries are a discovery source, not an approval — a server should pass review before it appears in the internal catalogue with production credentials.

Say: step through all seven frames. Do not read the JSON aloud; point at the highlighted fields as you go.

The first two frames are the ones people ask about. They are the model provider’s API — a different protocol, a different vendor, and not something MCP standardises. Saying “only the solid frames are MCP” resolves the confusion before it starts, and reinforces that swapping the model changes nothing below step 4.

The sentence to land at step 4: “Nothing in this exchange refers to a previous message. Every request carries its own protocol version and capabilities, which is why any instance behind a plain round-robin load balancer can answer it.”

On the headers: Mcp-Method and Mcp-Name exist so a gateway can route, meter and rate-limit per tool without parsing the body. That is what makes per-tool limits practical for us.

If asked “why not plain REST or gRPC?” — it is HTTP. The JSON-RPC envelope plus the discovery call is what lets one client work against every server without bespoke code.

10 · Calling an agent

Yes — a tool can be an agent

Nothing says a handler has to be a database query. It can run a whole agent — its own model, its own tools, several minutes of work — and from the caller's side it is still one tools/call. The question is whether that is the right shape, or whether you want A2A.

the handler runs an agentserver side
@mcp.tool() async def investigate_incident(incident_id: str) -> str: """Investigate an incident end to end: pull the timeline, correlate recent deploys, check error budgets and propose a likely cause. Takes a few minutes. Use for open Sev1/Sev2 only. """ agent = Agent( model="…", # the server's own model tools=[timeline, deploys, metrics], ) return await agent.run(f"Investigate {incident_id}")

The calling agent sees a tool. It has no idea another agent ran — and that is the point: the complexity stays behind the interface.

The governance catch worth naming

The approval gate covers the outer call. A person approving investigate_incident is not approving each of the forty steps the inner agent then takes. If those steps touch anything sensitive, the bounding has to happen inside the server — in the tools you gave it — not at the gate.

Tasks is an extension, not core

It moved out of the core protocol in this revision and is negotiated as io.modelcontextprotocol/tasks. A server must not return a task to a client that did not declare support — so check the client matrix before depending on it.

Why the server owns the model now

A server used to be able to borrow the client's model through Sampling. That is deprecated, and the migration is to call a provider API directly — which is exactly what an agent-behind-a-tool does anyway.

10 · The 2026-07-28 breaking change

The handshake is gone

This is the slide that changes what we build. MCP was a stateful, bidirectional session protocol. It is now stateless request/response. Toggle between the eras:

Removed in 2026-07-28What replaces it
initialize / notifications/initialized_meta on every request; server/discover if you want capabilities up front

Why an architect should care

The one pattern that had to change with it

A server sometimes needs something mid-call — a confirmation, a credential, a choice only the user can make. With no session to hold open, it can no longer call back to the client and wait.

So it returns instead, ending the request and handing back two things: the question it needs answered, and an opaque blob holding everything required to resume. The client gathers the answer and retries the original request, echoing that blob back untouched. A different instance can serve the retry — it verifies the blob, reconstitutes the context, and finishes the job.

This is Multi Round-Trip Requests, and it is the reason a server can stay stateless even for work that needs a human in the middle.

the interim resultresultType
{ "result": { "resultType": "input_required", "inputRequests": { "github_login": { "method": "elicitation/create", "params": { "message": "GitHub username?" } } }, "requestState": "<signed blob>" } }

The client retries with inputResponses, the same requestState, and a new request id.

requestState is attacker-controlled

It round-trips through the client. If it influences authorisation or business logic the spec says you MUST integrity-protect it — HMAC or AEAD — and reject anything that fails verification.

Bind it and expire it

Encode the authenticated principal, a short TTL, and a digest of the originating request inside the protected blob. That bounds replay and prevents cross-user reuse.

What this removes from the design

This is what removes the last reason to hold a session. Interactive, multi-step work now runs across a pool of identical stateless instances — no affinity, no shared store.

Presenter note

The point: an MCP server is now an ordinary stateless service. Same pipeline, same autoscaling.

Show: toggle old → new while talking. Old: handshake, session id, sticky routing. New: every request stands alone.

Say: “No session store, no affinity in the mesh, and a scale-in event no longer drops live work.”

On the second half: one sentence is enough — the server returns the question instead of calling back, and the client retries with the answer. The signed-blob detail is for whoever asks.

11 · Multi Round-Trip Requests

How a stateless server asks a question

A server sometimes needs something mid-call: a credential, a confirmation, a model completion. It used to open a request back at the client. Now it returns, and the client retries.

The point: how a server with no memory asks the user a question mid-call. This is the pattern people get wrong first.

12 · Transports

stdio for local, Streamable HTTP for everything else

Two supported transports. The choice is almost always decided by where the credentials live.

stdio

The host launches your server as a subprocess and speaks newline-delimited JSON-RPC over stdin/stdout. No ports, no auth framework — you inherit the user's environment and credentials.

{ "mcpServers": { "incidents": { "command": "node", "args": ["/abs/path/build/index.js"] } } }

Log to stderr, never stdout. stdout is the wire; a stray print() corrupts the protocol. Configure in claude_desktop_config.json.

Streamable HTTP

One endpoint that accepts POST. Each request gets either a single JSON object or an SSE stream scoped to that request, carrying progress notifications and then the response.

POST /mcp HTTP/1.1 Accept: application/json, text/event-stream MCP-Protocol-Version: 2026-07-28 Mcp-Method: tools/call Mcp-Name: get_incident // 200 → application/json (simple) // 200 → text/event-stream (streamed) // 202 → notification accepted

Send X-Accel-Buffering: no on SSE responses or nginx will buffer your stream into uselessness.

Validate Origin. Always.

Servers MUST reject invalid Origin with 403 — otherwise a web page can DNS-rebind into a local MCP server. Bind local servers to 127.0.0.1, not 0.0.0.0.

HTTP+SSE is Deprecated

The original 2024-11-05 two-endpoint transport is now formally Deprecated under the lifecycle policy and eligible for removal. Migrate.

Cancellation is a disconnect

On Streamable HTTP, closing the SSE response stream is the cancel signal. Stop the work; send nothing further for that request.

Presenter note

The point: the choice is almost always decided by where the credentials live.

Rule of thumb: stdio for anything on a developer's laptop; Streamable HTTP for anything multi-tenant, behind the gateway, or needing OAuth.

Watch out: on stdio, stdout is the protocol — a stray print() corrupts the stream. This catches every team exactly once.

13 · Build one

A working server is about thirty lines

Tier 1 SDKs are TypeScript, Python, Go and C#; Rust is in beta. Both examples below are complete servers — tool definition, handler, transport.

1  The tool definition

The decorator, the signature and the docstring become the JSON on slide 5 — the SDK derives it, you never write it by hand. This is the part that deserves real effort; everything else is boilerplate.

2  The handler body

Runs when a call actually arrives — step 06 of the walkthrough on slide 4. This is where your SQL, your API client and your credentials live. The model never sees any of it; it gets back only what you choose to return.

3  The transport line

One line chooses stdio or Streamable HTTP — the decision from slide 11. Nothing else in the file changes when you switch.

server.pyuv add "mcp[cli]"
from mcp.server import MCPServer mcp = MCPServer("incidents") @mcp.tool() # 1 → tools/list async def get_incident(incident_id: str) -> str: """Fetch an incident by ID, including its timeline and current owner. Args: incident_id: e.g. INC-4471 """ # 2 → runs on tools/call data = await fetch_incident(incident_id) if not data: return f"No incident {incident_id}." return format_incident(data) if __name__ == "__main__": mcp.run(transport="stdio") # 3 → transport

Deterministic list order

Return tools in a stable order. Clients cache the list, and stable ordering keeps LLM prompt caches hitting.

Ship ttlMs and cacheScope

Now required on tools/list, prompts/list, resources/list, resources/read and resources/templates/list. "public" lets shared intermediaries cache; "private" doesn't.

14 · What not to build on

Three client features are now Deprecated

The July revision adopted a formal feature lifecycle — Active, Deprecated, Removed — with a minimum twelve-month deprecation window and a public registry. Three long-standing features entered it at once.

Roots deprecated

Was: the client tells the server which directories it may operate in.

Instead: pass directories or files as tool parameters, resource URIs, or server configuration.

Sampling deprecated

Was: the server asks the client's model for a completion, so servers needed no API key of their own.

Instead: integrate directly with an LLM provider API from the server.

Logging deprecated

Was: notifications/message with a client-set level.

Instead: log to stderr on stdio, or emit OpenTelemetry.

Elicitation survives — and it's how you ask

Asking the user for input is still first-class. It just travels as an inputRequests entry in an input_required result rather than a server-initiated request.

Dynamic Client Registration → Client ID Metadata Documents

RFC 7591 DCR is deprecated as the registration mechanism, kept only for authorization servers that don't yet support CIMD.

Tasks moved out of core

Long-running work moved to the official io.modelcontextprotocol/tasks extension — covered properly on slide 9, where it matters.

Trace context is standardised

The spec now reserves traceparent, tracestate and baggage in _meta for W3C Trace Context, matching the OpenTelemetry semantic conventions for MCP. Distributed tracing across an agent's tool calls is a supported thing, not a hack.

"_meta": { "traceparent": "00-0af7651916cd43dd8448eb211c80319c -00f067aa0ba902b7-01" }

New error codes

-32020 HeaderMismatch -32021 MissingRequiredClientCapability -32022 UnsupportedProtocolVersion -32002 → now -32602 (resource not found)

Presenter note

The point: three features entered the deprecation register. Nothing new should adopt them.

Watch out: if any of our teams built on Sampling — and at least one did — stop on this slide. Twelve-month window, so it is schedulable, not urgent.

Say: elicitation survives. Asking the user for input is still first-class; it just travels inside an input_required result now.

15 · Before you expose anything

The threat model is the tool description

An MCP server hands a language model the ability to act on your systems. Most of the risk is not in the protocol — it's in what you chose to expose, and to whom.

Pre-launch checklist — tick as you go

0 of 10 cleared

Tool annotations are untrusted input

The spec is explicit: clients MUST treat annotations like readOnlyHint as untrusted unless the server is trusted. A hint is not a permission.

Never dereference a remote $ref

JSON Schema lets $ref point at any URI. Implementations MUST NOT fetch network refs by default — it's an SSRF primitive handed to whoever wrote the schema.

Don't put secrets in x-mcp-header

Mirrored header values are visible to every intermediary on the path. Route on region and tenant; never on tokens or PII.

Bound your schemas

anyOf/allOf/$defs nesting is a denial-of-service vector against your validator. Cap depth, subschema count, or validation time.

"The control plane must be correct every single time."
— Alex Salazar, MCP Dev Summit NA 2026

19 · Which systems first

The portfolio question, before the engineering one

Nothing here is hard to build. The decisions that matter are which systems we expose, in what order, and which ones we should not build at all — and those are portfolio decisions, not engineering ones.

Start by not building

A large part of the portfolio already has a server someone else maintains. Snowflake, Databricks, Salesforce, ServiceNow, Atlassian and GitHub publish official servers for their own platforms; Slack, HubSpot, Linear, Sentry, Neon and Vercel run remote endpoints; AWS, Snowflake and X offer managed ones. The remote ecosystem went from roughly 16 endpoints in January 2026 to about 30 by July.

So the first deliverable is an inventory, not code: for each system in the portfolio, does a vendor server already exist, is it supported, and does it meet our auth and audit bar? Adopting one is days of work. Building one is weeks.

The crown jewels, anything whose API you would have to build first, and anything with no owner. All three turn a two-week pilot into a programme.

17 · Recommendation

What I'd like us to do next

01 Run the portfolio scan first

For every system we would want an agent to reach: does a vendor server already exist, is it supported, does it clear our auth and audit bar? This is an assessment, not a build — a couple of weeks, no engineering headcount — and it will remove a meaningful share of the work before it starts.

02 Pilot exactly one we have to build

Chosen against the criteria on the previous slide: real existing demand, a stable API underneath, a defined access policy, read-only to start, and a named team that wants it. Three tools, two weeks. The point is the pattern, not the coverage.

03 Ask platform for the two shared pieces

A gateway (OAuth, per-tool limits, audit) and a private registry (what is approved to exist). These are the only components that must be built once and centrally — and until they exist, nothing else can safely compound.

04 Put it on the radar with a version

Adopt, targeting 2026-07-28 only. No dual-era servers, no new work on the deprecated Roots, Sampling or Logging features. One line in the standard saves a year of divergence across teams.
